## 数据架构

### 1.1 数据产生到变现

原理解析：

1. Excel：假设有一家水果店，日均订单几十单，通过Excel就能完成每日的订单管理；
2. 数据库：当日均订单1000单时，数据越来越多无法多人协作、经常卡死、硬盘损坏易造成数据丢失，SQL登场，数据库把数据按照表组织，一行一条记录、一列一个属性，链式存放在磁盘中，又可以称为行式存储，它非常适合对单条数据的增删改查，用户下单插入一行，改地址更新一行，毫秒级完成，多人访问不受影响、数据自动备份不怕丢失，一条SQL就能查任意结果；
3. 数仓：当日均订单10w单时，查看销售报表一条SQL查半个小时，当用户下单时所有用户都卡住了，因为统计SQL要对整张表做读取、求和、分组、聚合再出统计结果，把数据库和CPU内存全占满了，正常的查询和交易根本跑不动；

​	问题1：交易和分析是两种不同的需求，交易需要快、准、稳，每次只动几条数据；分析要扫海量数据做聚合；放在一个系统中必然会出现问题；

​	解决：拆分开专门做一个分析的系统，它将同一类的数据存在一起，订单表、金额表、时间表、订单状态表，这种方式叫列式存储；例如需要统计当日的交易额，只需要从磁盘读取对应的表，比行式读取效率更高；

​	问题2：数据是如何存放在数据仓库里；

​	解决：ETL工具=>Extract Transform Load 抽取-转换-加载；

​	抽取，通过数据库的标准查询接口拉取数据；

​	转换，主要负责把脏数据清洗干净（统一日期格式、去重删掉同一个订单重复录入记录、补全信息缺失默认值；

​	加载，和数据库按照用户表、订单表、支付表各存各的不同，数仓是按照分析主题分层存储，底层还是按照订单商品等维度规范分表，面向日常分析时会提前加工成主题宽表；例销售主题宽表（订单+支付+商品+物流）拼成一张汇总表（骑手宽表、运单宽表）这么做的好处是不需要跨多表进行查询；

​	通过ETL流程，数据从分散的数据库中抽取出来，通过清洗按照分析主题存入数据仓库；

4. 数据湖：移动互联网，数据量从GB级暴涨TB、PB级，而且80%以上数据是非结构化数据（视频、图片等）如果都存入数据仓库，成本会高到离谱而且数仓要求先建模再存储，对于没有用的历史数据都会清除，后续再想要使用时发现源数据没有了；

​	解决：挖个大池子，先把源数据囤着，它的核心是先存储后处理，底层使用是低成本介质（结构化、半结构化、非结构化）不需要提前定义表结构，需要分析时再写SQL解析；

​	存在的问题：可能出现缺乏统一管理，例如运营人员存日志为log1.txt，市场人员也存的是log1.txt，导致文件不清晰易错乱，最终80%的空间都被垃圾占用，容易形成“数据沼泽“；

5. 湖仓一体：数据仓库查询快、数据准但贵、装不下非结构化数据，数据湖能装、容量大但乱、查询慢；衍生出湖仓一体架构，核心逻辑就是将湖和仓打通，让源数据无缝互通、按需流动，所有的源数据想入湖，通过清洗、转换再做冷热分层；对于高频访问的热数据放在数仓中保证查询速度，冷门的历史数据转移到成本更低的数据库归档，节省存储成本（有点类似于前端的数据缓存或是浏览器缓存）数仓可以直接读取数据湖里数据，对于冷热数据能联合计算，最终生成的结果存入数仓或放回数据湖都支持，靠Delta Lake、Apache Iceberg这类表格式引擎就能实现，一种数据两种用法，完美平衡性能和成本；

6. 大数据：针对海量数据的一整套完整体系，并不是一种单一的工具或者架构；核心目标是从海量的数据中挖掘商业价值，它需要解决存、算、管、用四个核心问题；

   存：数仓、数据湖只是不同的组件，而MySql业务数据库只是大数据上游的数据来源，热数据使用Mysql存储，离线数据使用数仓存储，原始数据使用数据湖存储；

   HDFS就是数据湖早期经典的底层存储介质，本质上是一套分布式文件系统，单台服务器存不下PB级大文件，把文件切成默认128兆的小数据块分散存储到上千台普通服务器上，每个数据块存三个副本放到不同机器，就算某台机器故障也有其它备份；整个集群分为两个核心角色NameNode当总管，专门记录哪个文件的哪个块存在哪台服务器的索引信息，相当于图书馆的目录；DataNode当工人实际存放数据块，相当于书架；读写文件时先问NameNode找位置，再直接对应DataNode操作；

   但HDFS本质上也是一块超级裸硬盘，只管存文件没有标签和权限管理；因此数据湖在HDFS之上补充了一整套管理能力，数据接入工具将数据拉入湖中，源数据管理负责记录数据库里有什么数据存在哪，数据目录负责给数据分类打标签，还有细粒度的权限控制；目前行业主流已从自建HDFS转向云对象存储，无需运营、弹性扩容1TB年成本仅几十块性价比更高；

   算：数据库中存放海量数据，想要统计所有订单数据，全拿到一台机器上算根本扛不住；解决与分布式存储一样，将全量数据切分为一个个小分片，分给多台服务器并行计算，最后再将结果聚合起来；每天机器具体算什么？定义两个函数，map函数告诉每台机器本地分片里的每行数据怎么处理，例如算销售额就提取每笔订单的金额算出本地分片的总金额，reduce函数告诉系统所有机器的局部结果如何汇总累加；MapReduce大数据分布式计算的鼻祖，靠多机器并行处理原本需要几天的统计任务几分钟就能跑完；

   缺陷计算过程中的所有计算结果都会写入磁盘，频繁的磁盘IO拖慢速度，只适合对时效性要求不高的离线任务；Spark针对MapReduce慢的问题做了核心优化，把中间结果放在内存中计算，内存不够时才写入磁盘，速度直接提升上百倍，离线批量计算的绝对主流；

   Flink当业务需要实时数据时，批处理攒一批算一次的模式就不够用了；Flink是流计算框架，数据来一条就处理一条；

   管：管理模块只负责两个问题，任务怎么按时跑和数据怎么不出错；

   任务调度，所有计算任务都需要定时触发代表工具有Airflow它能够自动编排所有任务的依赖关系到点准时触发；

   数据治理，核心保证数据的质量和安全，比如统一数据统计口径、监控数据异常值、管控数据权限；

   用：所有技术最终都要服务业务，应用层就是大数据价值的最终出口；通常分为两类基础应用（BI报表数据大屏）和高级应用（推荐系统、风控系统）

7. 数据中台：大数据有了湖仓一体做存储，Spark和Flink做计算，任务调度和数据治理做管理，整套的技术问题解决；企业级管理问题出现，各部门数据不通，同一指标结果差异大，分析需要重复写SQL需求交付周期长，多业务线重复开发用户标签，人力浪费严重；为了解决部门间数据孤岛问题和重复开发，数据中台出现；数据中台不是技术而是一套管理体系，核心是将数据资产化和服务化，把企业常用的用户标签、商品指标、订单模型等加工成标准化的数据资产，封装成API接口，让数据可以变为直接被调用的服务；例如市场部需要做精准营销，不需要自己拉数据清洗算标签，直接调用中台的用户标签API查询所需数据（近30天用户访客性别）

### 1.2 电商完整流程

串联逻辑：

1. 用户下单，用户提交订单，数据写入Mysql数据库，毫秒级完成；
2. 离线数据同步，凌晨2点ETL把当天的订单、用户、支付数据，从数据库批量同步到数据湖，永久保存；
3. 数据中台离线加工，凌晨3点数据中台通过调度平台自动调动Spark任务，从数据湖读取原始数据加工成标准的数据资产，更新用户全量标签、计算商品销售指标、生成订单宽表，并把结果写入数据湖；
4. 离线分析，早上9点BI工具调用数据中台的销售指标API自动生成前一天的销售报表，用户留存报表，推送给老板；
5. 实时计算，用户在APP上每一次点击停留和滑动都会实时写入数据湖，Flink实时处理数据湖里的点击流和交易数据，更新用户的实时画像和实时销售数据并写回数据湖；
6. 在线推荐，用户再次打开APP时，推荐系统调用数据中台的用户实时标签API根据用户最佳的浏览行为推荐对应的商品，提升转化率；
7. 精准营销，市场部的营销系统直接调用数据中台的用户标签API，筛选出所需数据定向锁定，提升活动转化率；
8. 长期挖掘，数据研究通过读取数据湖近三年所有交易和行为数据，结合数据中台的标准化资产，训练新的推荐算法和销售预测模型，进一步提升转化率；

### 1.3 总结

1. 数据库：当下的在线交易
2. 数据湖：所有的历史数据
3. 大数据：怎么从数据里算出价值
4. 数据中台：怎么把价值变成可复用的服务
