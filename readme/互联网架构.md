## 互联网架构

### 1.1 单机架构

​	小网站用户量小、访问量极低，一台服务上装着应用程序和数据库，用一套开源的LAMP（Linux+Apache+Mysql+PHP）技术轻松搞定；（从零搭建）

### 1.2 应用与数据库分离

​	随着用户慢慢增长，应用和数据库经常抢资源；通过加机器把应用和数据库分开，应用服务器专门负责处理请求和业务逻辑，数据库服务器专们负责存数据做IO操作，可用性提升；（资源争抢）

### 1.3 应用集群和负载均衡

​	用户再次暴涨，单台应用服务器处理不过来，数据库扛不住大量查询，出现了高并发；单台服务器配置拉满也有上限，比如1秒只能扛住100个请求，出现500个请求如何处理？集群：配置5台服务器部署一模一样的代码；用户访问流量如何分配？负载均衡：开发中间层将请求均匀的分配到每台应用服务器，水平扩展，扛不住就加机器，一台服务器挂掉可以自动屏蔽流量，其它服务器承接保证系统不回崩溃，又称高可用；（高并发）

​	应用扛住了，大量请求穿透到数据库，数据库出现新瓶颈；

​	应用查询数据库原理：引用先发查询请求给数据库，数据库内部就先去内存缓冲区找数据，如果找到了就直接返回，没找到就在磁盘暴力查询，找出来再给到内存缓冲区，最后返回给应用；内存缓冲区读取比从磁盘读取快1000倍以上，如何都去缓冲区读取数据？服务器内存太小了；

### 1.4 多级缓存

​	将内存缓冲区单独抽离出来放大，存储经常访问的热数据实现快速查询；三级缓存：浏览器缓存、应用服务器本地缓存、分布式缓存（redis）用户每次请求先来浏览器缓存找，没有就去本地缓存找，再到分布式缓存最后才会到数据库；由于缓存放在内存中查询速度从毫米级ms变成微秒级us，数据库压力暴跌就算数据库故障缓存也能撑一阵子，可用性也提升了；（查询性能、数据库压力）

​	数据库缓存只存原始表数据，三级缓存是什么快、常用就缓存什么（页面、接口结果、静态资源、计算结果）缓存解决了热点读，但写请求和非热点读还是要打数据库，而且数据库有个特点，写比读慢的多，写会锁行锁表，并发一高就排队，对数据库进行分工；

### 1.5 分库分表

​	拆分读和写，主库负责写，从库负责读，通过数据同步来保证主从数据一致，读写分离；现实中互联网读多写少可以实现一主多从结构，分摊读写压力，数据库相互阻塞问题解决；（数据库读写阻塞、海量数据存储）

 1. 拆库拆表：当数据量越来越大，订单表和日志表越来越大单库单表撑不住，需要对数据库进行拆分；

 2. 垂直分库：按照业务拆分用户、商品、订单互不干扰；

 3. 水平分表：一张大表拆成多张小表，比如按照uid哈希分成多张表分散压力，配合数据库中间件对应用透明，不需要改大量代码；

    数据库层面从单点变成分布式，存储和并发能力可以无限扩展；

### 1.6 CDN反向代理

​	当系统业务发展至全国，有些用户访问快有些慢，而且应用服务器直接报漏在公网，容易被攻击；通过CDN加速服务器，在全国铺设多个节点，静态资源（HTML、CSS、JS）放在离用户最近的节点，用户通过域名解析获取到最近节点的IP去获取数据；通过Nginx反向代理，公网请求先到它再转发给内网应用服务器，它隐藏了真实应用服务器，防止被攻击，还可以做流量清洗、权限校验；（访问速度、系统安全）

### 1.7 搜索引擎和NoSql数据库

​	传统数据库遇到模糊查询、全文搜索、多维度统计出现力不从心；两个方案

​	搜索引擎（ElasticSearch）利用倒排索引让搜索秒级响应；

​	NoSql数据库（MongoDB）一个专门存非结构化半结构化数据而且支持高并发易扩展；

​	从简单的增删改查变成支持复杂检索和分析；（复杂查询）

### 1.8 分布式架构

​	应用侧出现问题，以两台应用主机的集群来说明；网站从一个小电商发展至集用户、商品、订单于一体的大平台，所有的功能代码全挤在一个应用里（巨石应用）改一行用户代码要发布整个应用，多个开发同时改代码冲突不断，想给订单服务加机器扛流量只能整个应用一起扩容，浪费资源，继续拆；

​	按照业务边界，用户边界的功能做成独立的用户系统、商品和订单做成独立的小系统，每个系统单独部署、单独发布、单独扩容；（业务膨胀、代码维护）

### 1.9 消息队列

​	用户下单需要查商品库存，生成订单，系统都拆分开了相互之间调用通讯难；通过RPC远程跨机器调用服务解决，但是相互调用的链路越来越复杂，无法快速找到目标去调用；通过服务注册与发现中心，管理所有服务器的地址，新增的服务都在此注册，相互之间的调用通过消息总管来查找调用；

​	服务之间相互调用相互等待，一个服务卡住整条链路跟着堵死，流量一高整体崩溃；如何让服务之间不进行相互等待？通过超大容量的智能收件箱，服务之间不用死等着对方立即回复，把消息扔进去排队后干服务自己的事，服务之间彻底解耦互不拖累，就算某个服务挂了，消息也不会丢失；削峰填谷：遇到流量突增还能把请求先存起来，按系统能力慢慢消化；

### 2.0 微服务架构

​	分布式架构拆是拆了但是还不够细，比如用户系统中登陆、信息、地址等等一大坨功能放在一起，不同的团队技术（Java、Go、Python）又不同，放在一个系统中较为臃肿；

​	按照一个服务只做一件事的原则，把系统拆到更细更小，将登陆、信息等做成单独服务，独立开发、独立发布、独立扩容，想用什么技术栈就用什么；极其灵活，面对订单暴增场景针对于某个服务直接加机器扛流量，其它不忙的服务完全不用动，资源一点不浪费，某个小服务出现bug绝不会拖垮整个网站，不同的技术团队相互独立开发，开发效率提高；

​	服务增多会导致调用关系形成“蜘蛛网”，出问题难以锁定，解决：全链路追踪，流量太多容易被冲垮，加上限流、熔断、降级自动保护系统；

​	服务太多不好管，解决：服务治理，统一监控日志权限；

​	对标大厂级微服务体系，轻松扛住千万级亿级流量，但服务越拆越细，运维直接歇比，从原来的几个服务拆分成几百个微服务，部署运维直接地狱难度，每个服务上线都需要配置环境和装依赖调整参数，稍微有点不一样就会出现我的电脑能跑但服务器跑不起来的bug；扩容赶不上、缩容效率低；（团队协作、极致弹性）

### 2.1 容器化和云原生

​	Docker容器将服务与运行环境打包成一个密封盒子，放到哪台服务器都能直接跑；不用配置环境，把每个微服务的代码依赖配置环境全部打包成一个镜像，一次打包随时随地运行，解决环境不一致的问题；

​	但是几百个上千个容器难以管理，全能大管家Kubernetes（K8S）安排容器自愈盒扩缩容，流量高时自动加容器、流量低了自动缩容器、容器挂了自动重启；就算有了K8S也是需要自己买服务器、租机房为了备战购买一堆机器平时全闲着，浪费资源，通过云服务平台要多少CPU内存带宽随时申请随时用，用完即释放按需付费；（运维、成本、自动化）

### 2.2 总结

​	从最初的一台小服务器到最终的弹性、自动化、高可用、能无限扩展的现代化架构，无论业务如何增长、流量如何暴增，都能稳定输出；

	1. 没有最好的架构，只有最适合业务的架构；
	1. 架构演进的本质：用空间换时间，用复杂度换性能；
	1. 围绕五大目标：高性能、高可用、可伸缩、可扩展、够安全；
